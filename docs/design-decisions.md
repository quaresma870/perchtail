## Scope and principles

- **Live, always fresh, read-only.** Every browse is a live listing and every open a fresh fetch. The push agent changes how a host is reached, not this rule. There is no scheduled mirroring and no persistent "run" concept. PerchTail stores no log content anywhere.
- **No Run/SyncState model.** "Last run", "run now" and run history were dropped from the admin UI. With no mirroring there is nothing to run, so an on-demand connection check (`POST /sources/{id}/check`, lists the base path) shows reachability instead. Since then, background reachability checks (`source_checks`) and the file-name index sweep do run on a schedule. They record metadata only, never content (#343, #304).
- **Security-critical logic first.** Grant resolution and the rule engine were built and unit-tested before any connector or UI, because everything else depends on them being correct.
- **No permission scoping inside one source's tree.** Folders group sources, not paths within a source. Rules already decide content visibility for everyone who can reach a source, so different capabilities per sub-path of one source were considered and declined.
- **Viewer stays read-only.** Editing a file or saving changes back to a source was dropped on purpose; every viewer feature (formatting, marks, bookmarks, compare, tail) is display-only and never changes the file or writes to the source. Writing back would break the core "PerchTail only reads from sources" rule for no strong reason.
- **Prefer simple all-or-nothing operations.** Operations that rewrite many rows (key rotation, migrations) run in one transaction with no partial-recovery or resume logic. Simpler, and nobody has needed resumability.
- **Breaking changes allowed before 1.0 when security needs them.** The KDF change in #51 made data encrypted under the old derivation unreadable after the upgrade; this was accepted under the 0.x policy ("0.x releases may include breaking changes between minors"), and it is why a key-rotation tool was built soon after. (#51)
- **The HTTP API is internal until 1.0.** It's the frontend's API and may change, so it isn't documented as a public interface. Scripted or GitOps-style management today goes through YAML import and export; personal API tokens (#253) are planned after 1.0 and don't exist yet.

## Architecture and storage

- **Alembic for migrations, with batch mode on SQLite.** SQLite can't add a foreign key with `ALTER TABLE`, so migrations that change constraints use `op.batch_alter_table` by hand. Autogenerated migrations don't do this and fail on first run.
- **FTS5 schema.** *Superseded:* the content index's FTS5 table lived outside Alembic and was rebuilt at startup when its schema changed. Now the `file_name_fts` FTS5 table is created by an Alembic migration (`e4b7c2d91a05_file_name_index`) and ensured again at startup (`ensure_name_index_schema` in `init_db`), so the schema has one versioned history (#303, #304).
- **Auth models built together with core models.** `Role`, `RoleGrant`, `User`, `SSOProviderConfig` and `AuditLog` were created with `Customer`, `Source` and `Rule`, not in a later stage, because auth touches every endpoint written afterwards.
- **Per-process state stays in memory.** Live agent connections (`AgentRegistry`), scratch bookkeeping (`ScratchStore`) and process uptime (`app/health.py`) are not stored in the database. They can't survive a restart, so a stored copy would only be a stale value.
- **Scheduler in its own module.** The shared APScheduler instance lives in `app/scheduler.py`, so `app/main.py` and the monitoring API can both import it without a circular import.
- **Generic key-value system settings.** Deployment-wide toggles and numbers are rows in `SystemSetting`, with defaults in code (`app/system_settings.py`). Any signed-in user reads them with `GET /system-settings`, because the frontend needs them; changing them with `PATCH /system-settings` needs `manage_system_settings`, and a few (redaction, password recovery, requiring MFA of local accounts, lowering the audit retention and turning off the auditing of folder listings) need a super admin. One shared mechanism replaces a bespoke flag per feature.
- **Typed settings helpers.** `BOOL_DEFAULTS` and `INT_DEFAULTS` are separate, each with its own `get_*`/`set_*`, so an integer setting can't be misread as `False` through the boolean helpers.
- **Deleted ids are never reused.** Tables other rows point at by id use `AUTOINCREMENT` (`app.models.NO_ID_REUSE`), and deleting a customer, folder or source deletes what points at it in the same transaction (`rbac.delete_scope_grants`, the source's file-name entries, alert state, scoped alerts, agent upgrade runs, severity patterns, redaction rules). Both halves are needed: cleanup alone still lets audit history and recent-sources confuse two objects sharing an id, and AUTOINCREMENT alone leaves dead rows that a later object could inherit (grants, indexed data).
- **Alerts scoped to a deleted object are deleted, not unscoped.** A null `source_id` on an alert means "every source the owner can view", which is wider than the original scope (`alerts.drop_scoped_alerts`).
- **The no-reuse migration also protects ids deleted before it.** Migration `47c9d392f28f` removes rows already orphaned, rebuilds the tables with AUTOINCREMENT and seeds each `sqlite_sequence` with the larger of the current max id and the highest `target_id` the audit log recorded for that table, so an id deleted before the upgrade isn't handed out again either.
- **Audit-chain backfill runs at startup, not in the migration.** The migration (`a1c3f6e4b2d7`) only adds `prev_hash`/`row_hash` and `audit_chain_state`; computing the historical chain is ordinary, testable Python (`backfill_chain_if_needed`), idempotent, run on every start before any seeding. Business logic is hard to test inside a migration, and a new hashed row written before backfill would be taken for the chain's tip. (Related: migrations that need an audit entry write to the audit outbox, which the next start signs; `app/audit_outbox.py`.)
- **In-memory, per-process state is acceptable for the single-process deployment.** The login lockout and the audit "Verify now" cooldown lock live in memory; a restart clears them. This matches the single-process-per-`DATA_DIR` SQLite model, and a restart is not something an unauthenticated attacker can trigger.
- **Single instance by design.** PerchTail runs as one process per `DATA_DIR`: SQLite (one writer, local disk, an FTS5 trigram table for the file-name index), all scheduled jobs inside the process, and some state only in memory (agent connections, login throttle, connector limits, scratch bookkeeping). Several replicas would mean several writers, uncoordinated copies of every job and state split across processes. There are twelve scheduled jobs now, and FTS5 backs only the file-name index; see [high-availability.md](high-availability.md).
- **One instance per `DATA_DIR`, enforced.** On startup, and for every online Alembic command, the process takes an exclusive OS lock on `DATA_DIR/.perchtail.lock`. A second instance refuses to start and names the holder, and there is no switch to turn this off. The OS releases the lock when the process dies, so it can't go stale (`app/instance_lock.py`, #334).
- **The supported HA ceiling is one replica with orchestrator self-healing.** Kubernetes or k3s restarts a single pod on crash or a failed `/healthz` probe, behind a plain Service and Ingress. That fixes "someone has to notice and restart it" with no code change, though it isn't zero downtime (`docs/high-availability.md`, "Solution 0").
- **Warm standby is the operator's own setup.** Active-passive (for example Litestream replication plus a standby that isn't Ready) works because the two are never live at once, but PerchTail has no built-in replication; the standby needs the same `CREDENTIAL_ENCRYPTION_KEY` and a copy of the credential salt, and the replication tool has to cope with the hourly `wal_checkpoint`.
- **Sticky sessions rejected as an HA answer.** Session affinity doesn't solve SQLite's single-writer limit: two users pinned to two pods still write to two independent file handles.
- **True active-active needs four pieces of work that haven't been done.** Those are a multi-writer database, shared login throttling, coordinated jobs, and shared agent connections and scratch. These are changes to PerchTail itself, not configuration, so it isn't supported; the code points at PostgreSQL (#306) as the way to several instances (`app/instance_lock.py`, `app/backup.py`, `app/name_index_store.py`).
- **No further HA tier ahead of demand.** Warm standby or multi-replica is built only once a real deployment's uptime need or measured load requires it. Until then the documented Solution 0 is the recommendation.
- **Graceful stop longer than the job drain.** The orchestrator's grace period must be longer than `SHUTDOWN_TIMEOUT_SECONDS` (20 s): `docker-compose.yml` sets `stop_grace_period: 30s` and the documented manifest sets `terminationGracePeriodSeconds`. Otherwise a rollout cuts running jobs off mid-run.

## Sources and connectors

- **Credential as an encrypted JSON blob.** `Source.credential_ref` decrypts to a JSON object (`username` plus `password` or `private_key`), not a bare secret, through `encrypt_credential`/`decrypt_credential`. One encrypted field can then carry every protocol's auth fields.
- **High-level protocol libraries.** SFTP goes through `paramiko`'s SFTP layer, not raw SSH channels, and SMB through `smbprotocol`'s high-level `smbclient` module (`scandir`, `open_file`), not raw SMB2 primitives. Both are close to `os`/`pathlib` semantics, which keeps connector code small.
- **Shared connector base.** `collectors/base.py` holds the shared `DirEntry` (now with `mtime`) and the `SourceError` types. Every connector exposes a `local_copy(source, path)` context manager: remote protocols fetch to a temp file, local yields the real path. Archive and gzip handling uses it the same way for every protocol. *Superseded for a `.zip` on SSH, SMB and WinRM:* copying the archive whole to list it, and again to open each member, made a few hundred MB over WinRM take tens of minutes per click. A zip keeps its index at its end and each member in one stretch, so those connectors now have `open_ranged`, which opens the file for one operation with the same checks as a fetch and reads at offsets, and `collectors/ranged.py` turns it into a seekable file zipfile reads in place, with a small block cache and read-ahead bounded by the member. `MAX_FETCH_MB` then counts what an operation transfers, the size is checked on every read so two versions of a file are never mixed, and the member's CRC catches the rest. A `.tar.gz` can't be read this way (it has no index and is compressed as a whole), so it, and everything else, still goes through `local_copy`.
- **Modification times.** *Superseded:* the content index tracked staleness by size alone because no connector reported mtime. Connectors now report `mtime` in `DirEntry`, and the file-name index stores path, size and modification time (#304).
- **Local plain files served in place.** Local sources serve plain files straight from disk, with no scratch entry and no `X-Scratch-Key`. A local `.gz` or archive member still goes through scratch, because decompressing or extracting produces new bytes that need somewhere to live.
- **WinRM reads through PowerShell, in chunks.** WinRM has no bulk file-transfer primitive, so content is read with PowerShell and returned base64-encoded. It is read in 4 MiB ranges (`FileShare.ReadWrite`, refused over `MAX_FETCH_MB` up front), not loaded whole, so large files don't sit in memory on either end. WinRM is the fallback to SMB, so this is an accepted trade-off. *Superseded for WinRS (0.7.0):* a range per round trip meant a new shell, a new PowerShell process and a new NTLM handshake for every 4 MiB, and the time went into the WS-Management `Receive` round trips of 150 KiB each, so a few hundred MB took tens of minutes. Since then, after one request for the size, a read uses one shell and one PowerShell process that opens the file once, after the junction check, and writes it as one base64 line per 3 MiB up to the size measured first, ending with `PERCHTAIL_END` and the byte count. PerchTail reads that output one `Receive` at a time and writes each whole line to scratch as it arrives, so neither end holds more than a line; an end without the marker, or with a different count, fails and deletes the partial file. Through the JEA endpoint the 4 MiB calls stay, on one runspace, since its role exposes no other read. Both ask for envelopes of 512000 bytes instead of the libraries' 153600, and ask again with 153600 when the server's `MaxEnvelopeSizekb` is lower (`winrm.envelope_fallback`).
- **Agent sources have no port or credential.** In the source editor, the `agent` protocol hides Port and the credential fieldset in favor of an enrollment section. Host stays as a free-text label. The real root is the agent's own `PERCHTAIL_BASE_PATH`, never anything the server sends, and an agent source can't have more than one root (`app/source_roots.py`).
- **Agent status replaces the manual check.** The sources list shows an agent source as connected, or when it was last seen, instead of a Check button. A check could only succeed while the agent is connected anyway, so the live registry state is the better answer.
- **`has_agent_token` in source responses.** Mirrors `has_credential`, so the UI can offer "Generate" or "Regenerate token" without the token ever being shown again.
- **Source responses carry place names.** `customer_name`, `folder_name` and `folder_path` (the ancestor chain) are included in source responses, so cards, the tree and search results can show "Customer / Folder" without a separate lookup.
- **SSH host keys are persisted and pinned.** The original bug (#50) was not `AutoAddPolicy` itself but that no known_hosts file was ever loaded or saved, so every host looked new on every connection; keys are now stored in `SSH_KNOWN_HOSTS_PATH`, and paramiko already refuses a changed key for a pinned host. Since then the policy is `SSH_HOST_KEY_POLICY`: `tofu` (a logging trust-on-first-use policy that records each pin's fingerprint) or `strict` (`RejectPolicy`). (#50)
- **Admin-created local-disk sources need an operator allowlist.** They stay (a bind-mounted host log folder is a real use, and e2e relies on one) but only under `LOCAL_SOURCE_ROOTS`, empty by default, which disables them; it is an environment setting so whoever controls the container's mounts decides, and no web-UI role can widen it. Without it anyone with `create_source` could expose the PerchTail host's database and secrets.
- **Local allowlist checked on every read, not only on save.** `collectors/local.py` re-checks it on each read (`base_dir`, called by `resolve_path` and `list_directory`), so a source created before the allowlist, or after it was narrowed, can't keep reading; the archive endpoints answer a clean 403.
- **Local reads are confined after resolving symlinks.** Reads stay inside the source's base path once symlinks are resolved, and symlinks pointing outside are left out of listings; this applies to the system log source too.
- **Links are judged by where they lead.** On local, SSH and agent sources, the rules are checked on the real path of every listing and read (where a link, the path itself or a folder above it, leads), and on the path asked for: both must be visible. A link to something the rules hide answers like a hidden path (404) and is audited as `link_target_hidden`. Without the rules, no link is followed (fail closed). SMB and WinRM sources keep refusing every junction and symlink, which is stricter.
- **The agent says where links lead, and the server decides.** An agent with the `links/1` feature (from 0.7) reports, in a listing, where each entry and the folder really are, and reads a file only when it really is where the server expects (`expect_real`); otherwise it answers with where it is, before reading anything, and the server asks again only if the rules show that target. The check and the read use the same open file, so a link swapped in between is refused, not followed. On Windows the agent resolves junctions and symlinks alike (`GetFinalPathNameByHandle`), so an 8.3 short name or another letter case also reaches the rules as the file's real name. Content is never read from an agent without `links/1`: it must be updated first (listing goes on), and the refusal only asks for the update.
- **Exclude rules ignore letter case everywhere.** A filesystem PerchTail can't tell is case-insensitive (Windows OpenSSH, a case-insensitive local mount) would otherwise let `SECRET/x` slip past `secret/**`. Failing closed, exclude rules, glob and `re:`, match without regard to case on every protocol; include rules keep the source's case sensitivity.
- **WinRM paths are quoted against every PowerShell single-quote character.** `_ps_quote` doubles `'` and the Unicode quotes PowerShell also treats as delimiters (U+2018, U+2019, U+201A, U+201B), so a path is only ever read as a string literal. JEA (`winrm_jea.py`, `docs/examples/jea`) is the recommended boundary on the Windows side; this keeps the plain WinRS path safe too.
- **Scheduled reachability checks.** A background `source_checks` job checks sources that are due (every 10 minutes by default, 0 turns it off), with backoff after repeated failures kept on the source row. Every real operation also updates the status, so all users see the same reachability (`app/source_status.py`, #276, #343). Only the last status and the failure count are kept, not the "short history per source" the idea described.

## Push agent

- **The agent dials out, and the server drives every command.** The agent holds a persistent connection and only answers `list`/`fetch` (now also ranged reads) when a user browses or opens a file. Nothing is pushed ahead of time, so an agent source is as fresh as an SSH one.
- **WebSocket transport.** Chosen over HTTP long-polling and gRPC. Starlette supports it with no extra dependency, it is easy from Go, and one duplex connection fits "server sends a command, agent answers".
- **Sync-to-async bridge in one module.** Connectors are synchronous code on FastAPI's thread pool, while the WebSocket lives on the event loop. `AgentRegistry.send_command_sync` uses `asyncio.run_coroutine_threadsafe` plus a blocking `Future.result(timeout)`, so `collectors/agent.py` reads like any other connector.
- **Connection state is live only.** `AgentRegistry.is_connected` is the only truth for "connected now". `Source.agent_last_seen_at` is informational and updated on each handshake, so it can't drift from reality.
- **Separate Go module.** `agent/` has its own `go.mod`, with logic under `agent/internal/agent` and a thin `main.go`, the same split the backend keeps from `app/main.py`.
- **`gorilla/websocket` as the only direct dependency.** It is the de facto Go WebSocket client and pairs directly with the Starlette server. Since GO-2026-6278 the agent uses a commit of its main branch (no release carries the fix yet), which brings `golang.org/x/net`.
- **Flat JSON envelope protocol.** Messages are `{type, id, path}` in, `{type, id, ...}` or `{type: "..._error", id, error}` out. A listing returns `{name, is_dir, size, mtime_ms}` entries (plus each entry's `target` and the listing's `real_dir` from an agent with `links/1`) and content travels base64-encoded, like WinRM. Since 0.5.3, `fetch` carries `chunk_size`/`max_bytes` and the agent streams `fetch_chunk` messages, ending with `fetch_result` and `streamed: true`, so neither side holds a whole file or nears uvicorn's 16 MiB message limit. The server still accepts `content_b64` from older agents. (#205)
- **Path safety re-implemented in Go.** `IsSafeRelativePath` (`internal/agent/pathsafety.go`) re-checks paths independently of the backend. The agent is the last line of defense before its own filesystem.
- **Reconnect with exponential backoff.** Delays run from 1 s to a 30 s cap, so an unattended agent survives host restarts and network loss. Since then, the backoff resets after a connection that lasted a minute and each delay is jittered (0.5x to 1.5x), so agents don't reconnect all at once after a server restart (#333).
- **No watching, no queue, no stored log data.** The agent answers exactly the command it gets and keeps nothing, enforcing the always-fresh design on its side. Upgrade binaries (#319) are the only thing it writes.

## Rules and visibility

- **Globs by default, `re:` for regex.** Patterns are globs unless prefixed with `re:`. Since then, both globs and regexes are compiled with RE2, so matching stays linear-time (#347).
- **Last match wins, in rule order.** This is the `.gitignore` model, so admins reason about include/exclude chains the familiar way.
- **Zero rules show nothing.** Visibility is explicit opt-in, never "show everything by default".
- **Path-traversal guard independent of rules.** `rules.is_safe_relative_path` runs before any rule check or connector, because a permissive rule could match a `../..` payload. It first split on `/` only, which let `..\` through on SMB/WinRM sources (a real bug). Since then it has been tightened to accept only canonical relative paths: it rejects backslashes, `:` (drive letters, NTFS streams), control characters and `.`, `..` or empty segments. Rules are matched on the path as written, so non-canonical spellings could otherwise dodge an exclude. `is_safe_windows_relative_path` adds Windows-specific checks.
- **Directory visibility.** *Superseded:* directories used to be always listed and only files went through the rules, which left excluded folders visible but empty. `is_dir_visible` now shows a folder only if some file below it could be visible under the same ordered rules. A later glob exclude covering the whole folder hides it, name and all. Regex includes are assumed to match anywhere, and only a glob exclude like `folder/**` reliably hides a folder.
- **Archive members are checked on their virtual path.** Listing, opening and downloading an archive member checks `{archive_path}/{member}` against the rules. Before this, a rule showing only an archive leaked its whole content, and a direct `/open` with any `member` bypassed the listing filter (a real bug fixed in M8). A whole archive is served only when no member is explicitly excluded (`_require_whole_archive_allowed`).
- **System source rule.** The seeded system log source has one include rule, `**/*`, rather than zero rules. Zero rules would show nothing, and `LOG_DIR` holds only the app's own logs on a super-admin-only source.
- **Non-canonical paths are rejected, not normalized.** `is_safe_relative_path` accepts only `/`-separated segments with no empty, `.` or `..` segment, no backslash, no `:` and no control characters; SMB/WinRM add `is_safe_windows_relative_path` (no trailing dot or space, no 8.3 short-name alias like `SECRE~1`). Every listing already produces canonical paths, and rejecting (400) leaves no gap between how the backend and the remote OS would normalize a path that could slip past an exclude rule.
- **Case-insensitive include rules only where the filesystem is.** SMB and WinRM sources, and agents that reported running on Windows (`Source.agent_os`), match rules case-insensitively (`rules_case_insensitive`); others keep include rules case-sensitive. Making every include rule case-insensitive would quietly widen them on Linux, where `App.log` and `app.log` are different files. Exclude rules ignore case everywhere (see "Exclude rules ignore letter case everywhere").
- **Agents on Windows: case sensitivity.** *Superseded:* agent sources stayed case-sensitive because the backend didn't know the agent's OS, with a regex workaround documented; the agent now reports its OS on connect and Windows agents get case-insensitive rules. (#189)
- **Two rule-editing modes.** The rule editor has a row mode and a raw-text paste mode (`frontend/src/lib/components/RuleEditor.svelte`, `PUT /sources/{id}/rules/raw`), one `include`/`exclude <pattern>` per line, with last match winning in both. This settles the open "raw-text paste UX" question.

## Access control and RBAC

- **Grant resolution walks source, then folder chain, then customer.** The most specific grant wins: a source grant, then the nearest folder going up, then the customer. The `is_system` short-circuit makes the system source reachable by super admins only, with no grant able to reach it.
- **Nested folders as grant scopes.** `Folder` is self-referential (`parent_folder_id`) under a customer, and a source optionally sits in one. `RoleGrant.scope_type` gained `folder`, generalizing source-beats-customer to any depth.
- **Global, not scoped, audit visibility.** Reading the audit log needs the `view_audit_log` global capability, not a customer/folder/source grant, because audit visibility is a global concern.
- **Ancestor folder names stay hidden.** `folder_path` in source responses stops at the scope whose grant makes the source visible (`rbac.folder_path_boundary`, `build_folder_visibility_context`). A role granted on a nested folder doesn't learn the names of ungranted parent folders. It is computed once per request, not per source, which also avoids N+1 queries.
- **Viewer tree from the RBAC-filtered source list.** The tree is built client-side from `GET /sources`, which is already filtered. No extra RBAC-scoped folder endpoint is needed, because a visible source implies its (bounded) path may be known.
- **Roles readable with `manage_sso`.** `GET /roles` (`require_read`) also accepts `manage_sso`, so the SSO page's mapping editor can fill its role picker. Creating and editing roles still needs `manage_roles`. Since then, delegated admins only see roles within their own authority, and the SSO group mappings don't name the others to them (`role_outside_authority`).
- **Folder management is an admin surface.** Settings → Folders and changing folders need `create_source`; listing them (`GET /folders`) also accepts `manage_roles`, for the role editor. Creating, moving, renaming and deleting a folder also need `manage_source` where it is (and, for a create or a move, where it goes), and the move rules mean a move can never widen the mover's access.
- **Folder moves validated on the server.** The "move to" picker hides a folder's own descendants, but `_validate_parent` in `api/folders.py` decides, so a concurrent move shows as a normal error.
- **Folder delete protection.** Deleting a folder that still has children answers 409.
- **Customer creation.** Customer creation was left out of the folder page and was only possible from the source editor. Since then, only a super admin creates customers.
- **Simplified grant editor.** The role editor uses a scope-type and target dropdown pair plus a table of grants, not a nested, searchable access tree. This proved the grant model at a fraction of the cost. Revisit when real data makes the dropdowns unwieldy.
- **Severity pattern gating.** Global severity patterns need `manage_system_settings`; per-source overrides need `manage_rules` on that source, like rules. This follows the existing split between deployment-wide and per-source concerns.
- **Delegated admins can't hand out more than they hold.** `rbac.role_within_authority`: a non-super-admin may assign, edit, duplicate, grant on, map an SSO group to, or act on a user holding a role only if it is not super-admin, its global capabilities are a subset of the actor's own, and its grants don't reach beyond the actor's. Each of `manage_users`, `manage_roles` and `manage_sso` had its own path to super-admin before this.
- **Acting on a more privileged account is blocked too.** Password reset, deactivate and edit check the target user's current role, because a password reset is an account takeover. Since then, only a super admin resets the password of, deactivates or changes the role of an account whose role has `manage_users` or `manage_roles`, even one within the actor's authority, so one delegated admin can't take over another (`_require_not_peer_admin`, audited with the reason `peer_admin`).
- **Data-access grants uncapped for delegated admins.** *Superseded:* a `manage_roles` admin could give any role grants on any customer, folder or source; grants are now capped by `grant_within_authority` (only what the actor holds at that scope and below), customers and folders are limited to the caller's reach, and a role holds at most one grant per scope. (#413, #428)
- **Built-in roles are immutable, even for super admins.** No rename, capability or grant change on "No Access" or "Super Admin". "No Access" is what every new SSO user lands on, so anything granted to it would reach anyone with an IdP account; "Super Admin" is the break-glass role.
- **The last active super-admin can't be deactivated or demoted.** So the break-glass account can't be removed by accident.
- **Role and grant changes are audited.** Role update/delete and grant update/delete write audit entries, not only creation.
- **A role still mapped from an SSO group can't be deleted (409).** Same as a role that still has users, rather than silently dropping the mapping.
- **`manage_sso` and issuer control.** *Superseded:* SSO users were matched by `sub` alone, so whoever controlled the issuer URL could sign in as existing SSO users, and `manage_sso` was to be treated as high-trust; accounts are now bound to `(external_issuer, external_id)`, and delegated SSO admins can no longer change the trusted IdP or group claim while a mapping gives a role beyond their own authority (`_require_trust_change_within_authority`); only a super admin deletes or turns off the provider.

## Authentication and SSO

- **Forced password change.** Admin-created local accounts must change their password at first login. `get_current_active_user` blocks every other endpoint until they do.
- **First super admin seeded with a random password.** `bootstrap.seed_initial_super_admin` runs only when no user exists. It generates the password (never read from config), so no long-lived secret sits in `.env`. *Superseded in form:* the password used to be logged once at WARNING; it is now written to `DATA_DIR/initial-admin-password` (mode 0600), deleted when the password is changed, and the WARNING only names the file, so the password never reaches the logs (#434).
- **`joserfc`, not `authlib.jose`.** authlib's maintainers deprecated its JOSE module in favor of joserfc, and the intent was a maintained JWT toolkit.
- **Plain `httpx` for the OIDC flow.** Discovery, code exchange and JWKS fetch are small named functions (`fetch_discovery_document`, `exchange_code_for_tokens`, `fetch_jwks`) instead of authlib's `OAuth2Client`. Tests can patch each step, the same "mock the client" convention the connector tests use.
- **ID token verified against the IdP's JWKS.** `verify_id_token` checks the signature, `iss`, `aud`, `exp` and `nonce` before trusting any claim. Userinfo alone is never trusted.
- **Stateless, encrypted `state`.** The OIDC state carries the nonce (and, since PKCE, the `code_verifier`) Fernet-encrypted (`encode_state`), with Fernet's timestamp as the 10-minute expiry (`STATE_TTL_SECONDS`), so no state table is needed. Since then, a `perchtail_sso_state` cookie (`HttpOnly`, `SameSite=Lax`, 10 minutes) also binds the state to the browser.
- **No account linking.** An SSO user is matched only by provider, issuer and `sub` (issuer added since, because `sub` is only unique per issuer). A username collision with a local account fails the sign-in instead of linking (audited as a failed SSO sign-in, and the browser goes back to the sign-in page with the neutral SSO error), because which identity wins is a security decision left for a real need.
- **`PUBLIC_BASE_URL` for the redirect URI.** The redirect URI comes from an explicit setting, not the request, so `X-Forwarded-*` headers from an unknown proxy are never trusted.
- **One enabled provider, enforced.** Enabling a second provider answers 409 (`_assert_single_enabled`), because the login flow must pick "the" provider unambiguously.
- **Local break-glass account.** Local accounts keep working while SSO is on.
- **SSO users provisioned on first login.** They get the "No Access" role unless a group mapping matches.
- **Group-to-role mappings are global.** `SSOGroupRoleMapping` (`order`, `group_name`, `role_id`) isn't tied to a provider, because only one provider can be enabled.
- **Mappings use last-match-wins.** The same ordered semantics as rules, not "most privileged wins", so admins reuse a familiar mental model.
- **`group_claim` names the claim.** The provider's `group_claim` setting (for example `groups` or `roles`, stored in the encrypted `SSOProviderConfig.config`) names the claim to read. *Since then*, an empty one no longer leaves roles alone: no mapping can match, so every SSO user gets "No Access" at each sign-in (except the last active super admin). `extract_claim_groups` accepts a string or a list.
- **Mapping applied on every login.** A user's role follows IdP group changes. The cost is that a manual role change doesn't survive the next login: the IdP is the source of truth for SSO users' roles. With no matching mapping, the user gets "No Access", new or existing, so leaving a group takes away what it gave; the last active super admin is never demoted this way.
- **Mapping editor on the SSO page.** It lives below the OIDC form, not on a separate page, because it only makes sense with that provider.
- **Login lockout keyed by username, not IP.** *Superseded:* `app/login_throttle.py` counted failures per submitted username only (5 failures lock for 300 s, answered 429 with `Retry-After`), with per-IP throttling left as a possible addition. It now counts failures per username and per client address: failures against one username lock it however many addresses they come from, and as many failures from one address, whatever the usernames, lock that address. An active local super admin with MFA on is counted per username and address, so an anonymous caller can't lock the break-glass account out everywhere (#434).
- **Lockout table bounded and fails closed.** *Superseded:* the tracked-username table was LRU-evicted at its bound; then a full table of live entries refused new usernames. Now both tables (accounts and addresses) are bounded and neither evicts (and so resets) a live entry: entries leave only when idle. When the account table is full of live entries, a new username isn't tracked and only the address limit applies to it, because refusing every new username let one anonymous caller lock everybody out. When the address table is full of live entries, a new address is refused (fail closed) (#434). Unknown usernames also cost the same argon2 work as real ones.
- **TOTP via `pyotp`, not hand-rolled.** Subtle mistakes in TOTP (time-step rounding, constant-time comparison) silently weaken security instead of failing, and RFC 6238 is stable.
- **Two-phase MFA enrollment.** `start_enrollment` stores a pending encrypted secret with `mfa_enabled` still false; `confirm_enrollment` enables it only after a valid code. A QR-scan mistake would otherwise lock the account out at the next login.
- **TOTP secret encrypted, backup codes hashed.** The secret is Fernet-encrypted (it must be fed back into TOTP at every login); the 10 backup codes are argon2 hashes (they only need an equality check). Hashing is the safer choice wherever plaintext is never needed again.
- **Backup codes shown once.** Only hashes are stored, so nobody, admins included, can recover a lost set; regenerating replaces the whole set rather than adding to it.
- **Password check and login finalization are separate.** `LocalPasswordProvider.authenticate()` checks credentials only; `complete_login()` sets `last_login_at` and audits `user.login` only after every required factor succeeded. Otherwise a password-correct, MFA-pending attempt would look like a completed, audited login.
- **A missing MFA code doesn't count against the throttle; a wrong one does.** Omitting the code is the client correctly stopping to ask for it; a wrong code is a guess, and counting it stops the code field being an unthrottled brute-force surface.
- **Structured error codes on MFA 401s.** The 401 `detail` is `{message, error_code}` with `mfa_required` or `mfa_invalid_code`, not a new status or response shape. FastAPI already accepts a dict `detail`, and every other endpoint's plain string keeps working.
- **TOTP codes are single-use.** `User.mfa_last_used_step` accepts only a code whose time step is newer than the last one used. `pyotp.verify()` alone would let a code be replayed within its acceptance window.
- **Enroll, disable and regenerate require the password.** All three re-confirm the password (`_require_password_reconfirmation`), and enrolling is refused while MFA is already on (disable first). Since then, disabling MFA that is on also needs a TOTP or backup code. A stolen session alone could otherwise replace a victim's secret and backup codes.
- **Password re-checks share the login throttle.** `_require_password_reconfirmation` (MFA endpoints, password change) uses `app.login_throttle` keyed by the same username. Same threat, whichever endpoint the guesses come through.
- **MFA state changes and their audit entry commit together.** `app/auth/mfa.py` functions don't commit (except `start_enrollment`, which has no audit event); the endpoint commits the change and its audit row in one transaction, per the `record_audit_event` convention.
- **MFA management is self-service only.** There is no admin "reset this user's MFA"; an admin can deactivate or reset a password. Left for its own design pass (own audit action, admin re-authentication, where it lives in the UI).
- **The MFA code step lives in the login form.** A password-correct, MFA-pending attempt has no session yet, so the code step is client-side state in `Login.svelte`/`lib/auth.ts`, re-submitting username and password with the code, not a post-session redirect like `must_change_password`.
- **OIDC only, no SAML.** SSO is OIDC, and the `saml` enum values in `app/auth/models.py` have no provider. OIDC covers the common IdPs (Entra ID, Okta, Google Workspace, Keycloak), and SAML comes after 1.0 only if there's demand (`docs/sso-setup.md`, README).

## Sessions and CSRF

- **Server-side sessions, not JWTs.** An opaque random token sits in an `HttpOnly` cookie, and its SHA-256 hash is stored in `AuthSession`. PerchTail holds production credentials, so revoking a session immediately (logout, deactivation) matters more than saving a database lookup per request.
- **`SameSite=Strict` is the CSRF defence; no CSRF tokens.** Every state-changing endpoint needs the session cookie (`__Host-perchtail_session`, or `perchtail_session` with `SESSION_COOKIE_SECURE=false`), which `Strict` withholds on every cross-site request, including top-level navigation; there is no `CORSMiddleware`, and the agent WebSocket uses a bearer token in the handshake header, which a browser page can't set. A forged request arrives unauthenticated.
- **Origin check as defence in depth.** `OriginCheckMiddleware`: on POST/PUT/PATCH/DELETE, an `Origin` (else `Referer`) header must match the request's own `Host`; a request with neither header relies on SameSite alone so curl and scripts keep working. Comparing with `Host` instead of a configured URL is the standard approach and works both behind a reverse proxy and through Vite's dev proxy, which strips `Origin`/`Referer` on proxied requests.
- **Origin check compares host and port only, not scheme.** Uvicorn behind a TLS-terminating proxy sees `http` while the browser's `Origin` says `https`, so a scheme-aware check would 403 every write, login included. Trusting `X-Forwarded-Proto` was rejected because the app port is also published directly, so a request bypassing the proxy could spoof it; SameSite stays the real defence.
- **Security headers on every response.** `SecurityHeadersMiddleware` sets a CSP with `script-src 'self'` (no inline or eval), `frame-ancestors 'none'` plus `X-Frame-Options: DENY` for older clients, `nosniff`, `Referrer-Policy: same-origin` (since then also `Permissions-Policy`, `Cross-Origin-Opener-Policy` and `X-PerchTail`). One global set because none of them blocks anything the app needs.
- **`style-src 'unsafe-inline'` is the one loosening.** CodeMirror 6 injects its styles at runtime through a `<style>` element, and a static SPA build has no nonce to give it.
- **No HSTS from the app.** HSTS belongs wherever TLS terminates (the reverse proxy).
- **Session list is self-service only.** `GET /auth/sessions` and `DELETE /auth/sessions/{id}` need only a signed-in user and are scoped to the caller's own sessions at query level. An admin view of other users' sessions is a different feature that wasn't asked for (deactivating a user or resetting their password already ends their sessions).
- **Sessions record the User-Agent, not the IP.** `AuthSession.user_agent` is captured at local and SSO login so rows can be told apart. An IP behind a proxy means trusting `X-Forwarded-For`; the User-Agent has no such trust question. (The audit log now records the client IP, through the separate `TRUSTED_PROXIES` setting, #424; sessions still don't.)
- **Ending your own current session is a normal logout.** The UI calls `POST /auth/logout` (clears the cookie, redirects) for the current session; another session is deleted with `DELETE`, and that device gets 401 on its next request, with no live push needed.
- **Sessions and MFA are personal pages, visible to every user.** *Superseded:* they were ungated Settings tabs (`/settings/sessions`, `/settings/security`) unlike the capability-gated rest of Settings; both now live in My profile (`SessionsPanel`, `MfaPanel`), and the old routes redirect there.

## Secrets and encryption

- **Hash-and-show-once tokens.** Agent enrollment tokens and the monitoring token are stored only as SHA-256 hashes (`Source.agent_token_hash`, `MonitoringToken`), the same pattern as session tokens. They are shown once at generation, and regenerating invalidates the old one, mirroring the admin password-reset flow.
- **Credential key rotation.** *Superseded:* a single static `CREDENTIAL_ENCRYPTION_KEY` with no rotation was accepted for v1, and rotating meant re-entering every credential. `python -m app.rotate_credential_key` now re-encrypts every secret and re-signs the audit chain in one transaction (#326).
- **Credential key derived with PBKDF2 and a per-install salt.** PBKDF2-HMAC-SHA256 with 600,000 iterations and a random salt in `CREDENTIAL_SALT_PATH` replaced a single unsalted SHA-256, and startup refuses `CREDENTIAL_ENCRYPTION_KEY=changeme`. A key derived without a work factor or salt is cheap to brute-force. (#51)
- **The Fernet key derivation must never change.** New derived keys (such as the audit-chain key) get their own KDF label instead of a change to the Fernet derivation, which would make every stored secret unreadable.
- **Key rotation is a CLI, not an endpoint.** `python -m app.rotate_credential_key`, run with the app stopped. It rewrites every encrypted row in one pass, which is destructive if interrupted and doesn't belong behind a web request; it builds old-key and new-key Fernet instances with `build_fernet()`.
- **The new key never comes from the command line.** It is read from `NEW_CREDENTIAL_ENCRYPTION_KEY` or asked for with `getpass`, because arguments end up in shell history and `ps` output.
- **Rotation is all-or-nothing and covers every encrypted value.** Source credentials, every SSO provider config (disabled ones too), MFA secrets, the SMTP password and alert webhook URLs are re-encrypted, and the audit chain is verified under the old key and re-signed under the new one, in one transaction; if anything fails to decrypt or the chain is broken, nothing is written. Re-signing a tampered chain would vouch for the tampering. (#326)
- **Rotation has a dry run.** `--dry-run` decrypts everything with the old key and reports the scope without writing, so an operator can check the old key first.
- **Rotation has its own guide.** `docs/credential-key-rotation.md`, not part of Quick start, because it's an occasional admin procedure.
- **Salt and known_hosts live on the persistent volume.** *Superseded in form:* the Dockerfile used to set both paths under `/data` explicitly; since 0.5.0 both default to `DATA_DIR` (`/data/db` in the image), and backups include them. Losing the salt breaks every secret and every audit HMAC, and losing known_hosts silently resets SSH pinning.
- **Startup refuses to create a new salt over existing encrypted data.** `bootstrap.assert_credential_salt_present` runs before anything derives a key; `CREDENTIAL_SALT_ALLOW_REGENERATE=true` is the explicit escape hatch. Failing loudly at boot keeps the original salt recoverable; failing later, one decryption at a time, doesn't.
- **No automatic move of a salt from the old container layer.** When a new image starts, the old container layer and its salt are already gone, so the step was documented in the CHANGELOG for the old container instead. (`app/data_layout.py` later moves the pre-0.5.0 layout inside the volume, which is a different case.)
- **External secret-manager references deferred.** These would be credential fields holding a reference resolved through a `SecretResolver` interface (Vault KV first). Tier 1 resolves the value once at import and stores it Fernet-encrypted; Tier 2 resolves it at each connection and stores only the reference. None of this exists (no `SecretResolver` in the code). The `${env:PERCHTAIL_IMPORT_*}` reference is the only indirection so far, and Tier 2 is worth its cost only when users ask for it.

## Audit log

- **Every audit write also logs.** Each audit row also emits a structured INFO log line.
- **Opens and downloads are audited.** Browsing a source's root records `source.open`, and downloads record `file.download`, the minimum audit bar that was missing until the connections home work.
- **Recent connections read from the audit log.** `GET /sources/recent` reads the caller's own latest `source.open` per source and re-checks live visibility, so a revoked grant can't leak a source through history.
- **Recent connections and the audit viewer stay separate.** They share a data source, but recent connections reads only the caller's own events and has no general audit filtering.
- **Admin-configurable retention.** `audit_retention_days` is a System setting (default 365, 0 keeps everything), not an env var. It resolved the long-open retention question. Since then, the minimum is 90 days and only a super admin can shorten it (#252, #383).
- **Audit retention is separate from log retention.** `LOG_RETENTION_DAYS` governs the app's rotated log files. Audit rows have their own setting and their own purge job (`app/audit_purge.py`), whose cadence is an env var (`AUDIT_PURGE_INTERVAL_SECONDS`, daily), because only the retention period was a real decision.
- **Filter values come from the data.** `GET /audit/filters` returns the actions and target types actually present (and now named targets), not a hardcoded list that goes stale. The API also accepts a trailing `.*` on an action as a prefix match.
- **Filtering by type and action is a requirement.** Narrowing by type and action is a first-class part of the page, not an extra.
- **No user filter in the UI.** The API accepts `user_id`, but the page has no user picker: it would need raw ids or `GET /users`, which a `view_audit_log`-only role can't call. Each row shows the username instead.
- **Audit page toggle.** The audit page can be turned off with `audit_view_enabled`, using the shared `SystemSetting` mechanism. Since then, turning it off also makes the API answer 404 to everyone but super admins.
- **Tamper evidence is an HMAC hash chain.** Each `AuditLog` row's `row_hash` covers its content and the previous row's hash, so changing or deleting any row breaks everything after it; `verify_chain()` stops at the first unexplained break, since nothing after it can be trusted. Simpler than a separate append-only store or a signature scheme.
- **The chain is keyed.** The HMAC key (`audit_chain_key()`) is derived from `CREDENTIAL_ENCRYPTION_KEY` and the salt with its own label. A keyless chain with this project's public algorithm could be recomputed by anyone holding only the SQLite file; full server compromise (key included) would need external anchoring, left as a possible future step.
- **Verification has its own interval.** `AUDIT_INTEGRITY_CHECK_INTERVAL_DAYS` drives its own job, separate from the purge interval and the retention, and is in days for readability. Tying it to retention would let a retention change silently change how often tampering is caught.
- **Verification runs daily.** *Superseded:* the default interval was 365 days; it is now 1 day. (#424)
- **The purge advances a chain anchor before deleting.** `AuditChainState` keeps the newest purged row's id and hash, and verification expects the first surviving row to chain from it. The same singleton row holds the last verification result for the Audit log banner.
- **The purge deletes an id prefix, not a timestamp range.** It deletes only rows with `id < first_not_old_id` (the smallest id among rows not old enough), in chunks of 5000 since #346, holding the chain maintenance lock per chunk. Under concurrent writes timestamp and id order can differ, and deleting from the middle of the chain would look like tampering.
- **"Verify now" is open to audit-log readers, with a 30-second cooldown.** `POST /audit/integrity/verify` needs `view_audit_log`, since it only recomputes and stores a status; a call within 30 s returns the stored result, behind a process-wide lock. A full pass is an O(n) HMAC walk that a low-trust role could otherwise trigger in a loop.
- **Status starts as "unknown".** Until the first check runs, the banner shows unknown rather than ok, so it never claims an unchecked chain is intact.
- **Concurrent audit writes.** *Superseded:* a narrow race between two writers was accepted and documented; `chain_new_entry` now takes SQLite's write lock (a no-op UPDATE) before reading the tip, and breaks left by the old race can be recorded as known by a super admin, after which verification accepts only those rows. (#213, #217)
- **Concurrent audit writes on PostgreSQL: a transaction-level advisory lock.** Under READ COMMITTED two transactions would read the same tip, and the no-op UPDATE takes no lock there, so `chain_new_entry` takes `pg_advisory_xact_lock` with a fixed key before reading the tip; it is released by the commit or rollback. A second writer waits for it, in this process or in another one on the same database, and then sees the first one's row. The row's id is drawn from its sequence when it is flushed, still under the lock, so ids follow the chain's order; a rolled-back write leaves a gap in the ids, which verification doesn't mind, since it follows `prev_hash` in id order. Rejected: `SELECT ... FOR UPDATE` on the chain state row, which needs that row to always exist, and `LOCK TABLE auditlog`, which also blocks readers. (#306)

## Live browsing, scratch and the viewer

- **Scratch store design.** Each open gets its own scratch file in a reference-counted store. Files are purged when released, by an idle sweep, and by a size guard that evicts the oldest unreferenced first. `.gz` is decompressed transparently, and the same fresh-fetch and purge rules apply to extracted archive members.
- **Path and member as separate parameters.** `open`/`download` take `path` and an optional `member` rather than one combined virtual path, which avoids ambiguous prefix parsing. Only one level of archive is opened: an archive inside an archive is served whole, after the whole-archive check.
- **Browsing inside archives.** *Superseded:* expanding an archive listed its members flat, and a folder member was a dead end because `/browse` couldn't recurse inside an archive. Browse paths can now go into an archive (`logs/a.zip/sub/dir`). The member list (folders included) is fetched once when the archive is expanded and kept while it's open (#347).
- **Lazy tree.** The explorer fetches a folder's children only when it is expanded.
- **Folder ZIP download.** `GET .../download-zip` fetches every contained file fresh to zip a folder, because the viewer spec asks for "a single file or a zipped folder". Since then, the ZIP is streamed (#345).
- **Deep links to a line.** `#/viewer/:id?path=...&line=...` opens a file and jumps to the line through `CodeMirrorPane`'s imperative `scrollToLine()`, called via `bind:this` rather than a reactive prop. It was first built for search results and is still used.
- **Find all is a pure scan.** "Find all in current document" scans the tab's content string (`lib/find-in-document.ts`) instead of using `@codemirror/search` cursors. It needs no new dependency and is unit-testable without an editor view.
- **Find all coexists with step-through find.** Highlight-and-step through matches and the list of every matching line are two complementary tools. Since then, both are driven from one find bar (#299).
- **Find all controls.** *Superseded:* Find all had its own query, case and regex controls, independent of Ctrl+F, opened by a toolbar toggle. One find bar now feeds the editor highlights, the count and Find all (`FindSpec`), so both always agree (#299).
- **Find all result cap.** *Superseded:* results were capped at 5000 with `truncated: true`. There is now no cap. The scan keeps only matching line numbers and works out highlights only for rows on screen, so huge logs with millions of matches stay usable.
- **View modes are toolbar toggles.** Wrap, show all characters, mark highlighting, tail and compare are stateful toolbar buttons (click on, click off), not modals or settings pages; a mode that needs a second input (compare) arms the button, and the next file picked completes it.
- **Per-tab state lives on the tab, not in the editor pane.** Bookmarks, wrap, show-whitespace, marks, format and following are fields of `Tab` (`lib/viewer-tabs.ts`) passed down as props. The CodeMirror pane is one instance reused across tabs, so state inside it would show one tab's settings on another's content.
- **Bookmarks and marks are session-only.** Pure client state, never persisted or sent to the server.
- **CRLF is detected in the raw content.** `findCrlfLineNumbers` scans the fetched string before CodeMirror splits it, and the CRLF glyph is a zero-width widget at the line end. CodeMirror's line splitting has already removed the `\r` from `Line.text`.
- **One stepper for problems and bookmarks.** `lib/line-cycle.ts`'s `nextLine`/`previousLine` (wrap-around) serves both; `nextProblemLine`/`previousProblemLine` are aliases. It's the same operation.
- **Reload takes a new scratch reference, then releases the old one.** The scratch key is deterministic (hash of the user's session, source, path and member; the session part means a viewer only ever releases what its own session opened), so Reload calls `/open` again and then `/close` once for the previous reference.
- **Copy with line numbers is extra, not a Ctrl+C override.** The browser already copies plain text; line-numbered copy is its own toolbar action (`copySelectedLines`).
- **Syntax highlighting is chosen by file extension and is optional.** `languageForFilename` maps `.json`, `.xml`/`.html`/`.htm`/`.svg` and `.js`/`.mjs`/`.cjs`/`.jsx`/`.ts`/`.tsx` to CodeMirror languages; anything else (most logs) gets none, and archive members use their own name. Highlighting coexists with severity indicators and is never needed for a file to open.
- **Compare uses `MergeView` and diffs raw content.** `DiffPane.svelte` remounts per target (`{#key}`), the target is a one-shot snapshot (any source, #162, or an open tab), and switching tabs clears it; both sides are the raw fetched content, never the beautified display. Diffing formatted against raw text would show whole files as changed.
- **Beautify/minify for JSON and XML only, display-only.** JSON through `JSON.parse`/`stringify`, XML through a small indenting printer with a `DOMParser` well-formedness check; content that doesn't parse stays raw with an inline error. JS was left out because it needs a real parser (a much heavier dependency) and logs rarely embed it.
- **Reload and Tail keep the active format.** Resetting the format on each reload made Tail flip a beautified tab back to raw every poll; if new content no longer parses, the display falls back to raw on its own. A format change clears the tab's bookmarks, since they are line numbers in what's displayed.
- **Tail is client-side polling, the same for every protocol.** It polls only for the tab that is active and following, not while the browser tab is hidden, at `tail_interval_seconds` (default 2). An agent-only "watch" over the WebSocket was rejected because SSH, SMB, WinRM and local sources have no persistent connection to extend.
- **Tail reads only what was appended.** *Superseded:* each poll used to re-fetch the whole file; now `GET /sources/{id}/follow` returns the bytes after the viewer's offset through each connector's `read_range`, plus the size and a hash of the first 64 bytes so rotation or truncation reloads from the start, and the pane appends in one transaction. `.gz` files and archive members still reload whole (the server answers 409 `follow_unsupported`). (#254)
- **Tail limits.** Tail keeps the last 200,000 lines of a tab (older ones are dropped, with a note); a file that leaves the source stops Tail and keeps the tab's content, marked missing. (#347, #272)
- **Scroll position survives editor rebuilds.** `syncView` keeps the view at the bottom if it was there, else at the same offset, when the content rebuilds the state, and appends in place during Tail. Resetting to line 1 would make Tail unusable on large files.
- **The editor state is built from the whole text only when the text changes.** Building it takes seconds with a file of hundreds of megabytes, so each tab's `EditorState` is kept by tab key in memory (`lib/editor-states.ts`) and put back, with its selection and place, when the tab is shown again or the Viewer comes back from another page; it is forgotten when the tab closes and on logout. Severity patterns, language, Wrap, Show chars, bookmarks and highlights live in CodeMirror compartments, reconfigured in place. Only text that changed other than by appending at the end (Reload, Tail dropping old lines, a rotation) or a format change rebuilds it (`lib/editor-sync.ts`, `planSync`). Severity patterns are kept per source in the same module, and a source without any uses one shared empty list, so patterns arriving for another source change nothing. Coming back to the Viewer asks again, in the background, for the patterns of each source with open tabs, and replaces a source's list only when it highlights differently (`refreshSeverityPatterns`): a change in Settings reaches the open tabs by reconfiguring the severity compartment, and an unchanged list leaves the editor as it is. A source's patterns are forgotten when its last tab closes, so the next file opened from it asks for them again.
- **Scratch on plain disk.** `SCRATCH_DIR` is an ordinary directory (`/data/scratch` in the image), preferably on its own disk, protected by a free-space guard (`SCRATCH_MIN_FREE_GB` / `SCRATCH_MIN_FREE_PERCENT`, 507 when low) and emptied at startup. A tmpfs is neither required nor documented.
- **The built-in log viewer doesn't hide DEBUG files.** The system log source gets a single `include **/*` rule (`app/bootstrap.py`, `seed_system_log_source`), because `LOG_DIR` holds only the app's own logs and only super admins can open it.

## Search and indexing

- **Content index.** *Superseded:* full-text search stored per-line snippets of log content in an FTS5 table, filled by a background indexer for sources that opted in (off by default), and matched content and file path. It was removed with the Search page and `GET /search`, so nothing from the logs is kept at rest. The replacement is a file-name index (names, sizes, mtimes only, on by default) and one search in the explorer (#303, #304, #300).
- **Content index details.** *Superseded:* these went with the index (#303): staleness by size, the search box wrapped as one quoted FTS5 phrase, `.gz` indexed but not archives, binary and oversize files skipped, and path-only hits de-duplicated per file.
- **Escape before highlighting.** Any server-built highlight of log text must HTML-escape the text before splicing in markup. FTS5 `snippet()` rendered with `{@html}` was a stored-XSS hole, fixed with a regression test. The content index is gone, but the lesson stands: webhook hits now carry plain-text `line`, and the snippet code was removed (#303).
- **Source matches resolved client-side.** Host and name matching runs in the browser over the already-fetched, RBAC-filtered `GET /sources` list, not in an index. It is always current and costs no extra round trip. It started as Search's "Sources matching" section and was kept by the unified search (#300), which matches name, host, customer and folder.
- **Explorer filter.** *Superseded:* the home page's "All connections" box matched folder, customer or host but deliberately not the source's name (`lib/connection-filter.ts`), and a query force-expanded the tree. The unified search box now matches name, host, customer, folder and file names, and its results replace the tree while text is in the box (#300).
- **No archive-member content indexing.** *Superseded:* whether to index `.zip`/`.tar.gz` members for full-text search became moot when the content index was removed so that nothing from the logs is kept; only file names are indexed (#303, #304).

## Alerts

- **Alerts match content, not operational health.** "Alerting" means notifying when new lines match an alert's query. System health is covered by the monitoring endpoints.
- **Evaluation.** *Superseded:* alerts rode on the content index, ran at the end of each indexing sweep, re-searched changed files past `reported_through_line`, and could only watch sources with indexing on. They now run as their own `alert_pass` and read only what was appended since the last pass, the same ranged read as Tail. The files come from the file-name index, matched by a glob (never compressed files or archives). Rotation is detected by size or a first-bytes hash. Nothing of the content is kept (#305).
- **Alerts never match on path.** Alerts match lines only, never file names: a path doesn't change when a line is appended, so a path match would fire on every pass.
- **Webhook, not email.** A generic JSON webhook needs no new infrastructure and covers Slack, Teams and generic receivers. Email notifications are planned separately (#251), now that an SMTP server can be configured (Settings → Email, #244).
- **Test button.** `POST /alerts/{id}/test` sends one sample call in the real payload shape (`test: true`), so the receiver can be checked without waiting for a match. Since then, a user can send at most 5 tests a minute (`TEST_CALLS_PER_USER`, 429 past that).
- **Access re-checked at every pass.** Scope is resolved against the owner's current access at each pass (`scope_source_ids`, `visible_source_ids`), and the owner must still be active with `manage_alerts` (`owner_may_alert`). Revoking access stops the alert without editing it.
- **Alerts are personal.** An alert belongs to its creator, and list, edit, delete and test are owner-only. They aren't placed in the grant tree because an alert is like a bookmark. RBAC still limits which sources it watches. Since then, creating alerts also needs the `manage_alerts` global capability.
- **Alerts page tied to Search.** *Superseded:* the Alerts page was gated by `search_view_enabled` and had no in-place edit. The Search toggle is gone with Search (#303), and alerts can be edited in place.
- **Webhook SSRF guard.** Webhook URLs must resolve to public addresses (`app/webhook_safety.py`). They are checked on create and update (422) and again at send time against DNS rebinding. Since then, the send is pinned to the address that was checked (`resolve_pinned_webhook_target`). Redirects aren't followed. (#49)

## Import and export

- **One YAML file, no CSV.** *Superseded:* the plan was YAML first with CSV as a simpler second format; only YAML was built (`app/config_transfer.py`, `docs/bulk-import.md`), because its nested customer, folder, source and rule shape is the actual data model. JSON for people was rejected as the same tree but harder to edit by hand, and it wasn't added either (#179).
- **Template and preview before apply.** The import screen offers a template with an example source, and `POST /admin/config/import` is a dry run by default that lists every create or change, or every problem with its place in the file. Nothing is applied blind.
- **Matched by name, idempotent, additive.** A customer is matched by name, a folder by name under the same parent, and a source by name within its customer (moving it when it sits under another folder). Re-importing the same file changes nothing, and nothing absent from the file is ever deleted, so the file can be kept as configuration as code. An import can't change an existing source's protocol.
- **All or nothing.** The whole file is checked before anything is written and applied in one transaction. Unknown keys are reported as problems, not ignored, and a file is limited to 1 MB and 5000 sources.
- **Credentials never exported, never shown.** Export leaves credentials out, and re-importing keeps each source's existing one. The preview only says whether a source needs a credential (`needs_credential`) and never shows a value.
- **Credentials go through the normal encryption path.** Imported credentials are encrypted with the same `encrypt_credential` (Fernet) as the source editor, with no separate code path for writing credentials.
- **Credential sources at import.** *Superseded:* the plan was a structure-only file plus a separate credentials-only upload keyed by name. What was built takes, in order, credentials typed in the import screen, the file's `credential` block (inline or `${env:PERCHTAIL_IMPORT_*}`), then the source's existing credential. The env reference is limited to the `PERCHTAIL_IMPORT_` prefix so an import can't read the server's other settings, such as the encryption key.
- **Audit by count and change, never payload.** Each created or changed customer, folder and source gets its own audit entry marked `"via": "import"`, with a credential change recorded only as `"replaced"`. One `config.import` entry carries the totals, and exports are audited as `config.export`.
- **Super admins only.** Import and export need the super-admin role (`require_super_admin` in `app/api/config_transfer.py`).
- **Not in the file.** Agent enrollment tokens, a WinRM source's JEA endpoint, roles, grants, users, SSO, system settings, severity indicators and alerts aren't in the file. Tokens are shown once, and the rest isn't per-source structure.

## Health and monitoring

- **Structured health endpoint.** `GET /monitoring/health` does a real database round trip and returns structured status (ok / degraded / error, documented in `docs/monitoring.md`), next to the liveness `/healthz`.
- **Unauthenticated `/healthz`.** *Superseded:* `/healthz` was an unauthenticated liveness check. `/healthz` and `/readyz` now answer only a local caller without proxy headers, an address in `PROBE_ALLOWED_NETWORKS`, or a holder of the monitoring token, so a refused probe learns nothing about the instance (#366, #330).
- **One deployment-wide monitoring token.** Not tied to a user. It is generated from Settings → Monitoring under `manage_system_settings`, stored hashed and shown once.
- **Zabbix reads the same endpoint.** Zabbix uses an HTTP agent item and JSONPath preprocessing on the one JSON endpoint, never Zabbix-specific endpoints. Since then, templates ship in `docs/examples/zabbix/` (#332).
- **Prometheus as a thin wrapper.** The health response was shaped so a Prometheus exporter could be a thin wrapper over the same internals. That is now built: `/metrics` comes from the same computation as `/monitoring/health`, behind the monitoring token (#331).
- **App version in one place.** `app/version.py` is the single source of the app version, also passed to `FastAPI(version=...)`.

## Frontend and UI

- **Vite + Svelte + TypeScript.** Chosen for the smallest runtime and build of the SPA options, which matters for a single-container app. It has no virtual-DOM overhead for forms, a tree and an editor, and integrates easily with CodeMirror 6.
- **Hash routing, served by the backend.** The built SPA is mounted as static files at `/`, after every API router so it can't shadow a route. Hash routing means the browser only requests `/`, so no catch-all rewrite is needed and PerchTail needs no proxy of its own.
- **Everything admin under one Settings entry.** Admin pages share a sub-nav, and every route has a `/settings/...` prefix. The Settings entry and its Sources tab are always shown, because Sources was never capability-gated.
- **Shared sub-nav component.** `SettingsNav.svelte` is embedded at the top of each settings page instead of a nested router, because `svelte-spa-router` has no layout or outlet concept.
- **`/settings` lands on Sources.** A bare `/settings` redirects to `/settings/sources` with `replace`, not `push`, so it adds no history entry.
- **Dev proxy lists every API prefix.** Every API path prefix must be listed in `vite.config.ts`'s dev proxy (`/sso` and `/search` were once missing). This only affects `npm run dev`, since production serves the API and SPA from one process.
- **System source protections.** The system source shows a "system" badge and has no edit or delete actions in Settings → Sources.
- **Tree as an alternate view.** The tree (customer, folder, ..., source) is an alternate view over the same filtered list, not a replacement for it. Since then, the default view is an admin setting and each user's choice is saved on the server (#156, #273). Expand and collapse state stays in memory only.
- **Distinct tree component names.** `ConnectionsTree.svelte` (sources by customer and folder) is named apart from `FolderTree.svelte` (a source's remote directories), because "expand" means different things in each.
- **Tree built in memory.** `buildConnectionTree` builds the tree from the flat source list. Folder ids are global, so one map de-duplicates folders. The system source (no customer) goes under a "No customer" bucket.
- **Shared folder-nesting logic.** The folder picker and the folder admin page share `lib/folder-tree.ts`, so they don't keep duplicated code.
- **Severity indicators are configurable, global and per source.** `SeverityPattern` (level, pattern, `pattern_kind`, enabled, `highlight_line`, `include_in_navigation`, nullable `source_id`) with seeded global defaults (`DEFAULT_GLOBAL_PATTERNS`); matching runs in the browser (`lib/severity-highlighting.ts`). Replaces the hard-coded regexes.
- **Per-source severity patterns override, not merge.** A source with any patterns of its own uses only those (`effective_patterns`, `GET /sources/{id}/severity-patterns/effective`); otherwise the global set. Same "most specific wins" shape as grants, and simpler than layering.
- **Severity matching differs from rule matching.** A glob-kind severity pattern is a literal, case-insensitive substring anywhere in the line; a regex-kind one is used as-is, case-insensitive. The `re:` prefix and `PatternKind` are shared with rules only for UI consistency; the path glob compiler (`_compile_glob`) is anchored and segment-aware, built for paths, not line text.
- **Problem navigation is a per-pattern flag.** `include_in_navigation` decides which matches next/previous-problem steps to, rather than a fixed warn-or-worse floor; defaults enable it for error and warning, not info and debug. Admins decide what counts as a problem.
- **No raw-text paste mode for severity patterns.** A row editor is enough for the handful of patterns per level; a bulk format would need per-line level tagging for little benefit. Revisit if real use shows otherwise.
- **Mark highlighting is separate from severity indicators.** `lib/mark-highlighting.ts`: ad hoc, session-only, typed by the viewer, reusing the `re:` convention only for the glob/regex switch; colours come from a fixed 6-colour palette (lowest unused colour first, then cycling), not a colour picker. It's a quick highlight-and-discard tool.
- **The mark button is labelled "Highlight".** Avoids a clash with the bookmark stepper's "mark" labels, even though the code and Notepad++ call it "mark".
- **Severity regexes run in the browser, held to the rules' syntax and limits.** The backend never runs them, but they run in every viewer's browser, so they are saved only in RE2 syntax (no backreferences or lookaround) and at most 1000 characters, as rules (`parse_pattern_or_400`). The browser's own regex engine still backtracks, and one call to it can't be interrupted, so the viewer runs them in a Web Worker (`lib/severity-worker.ts`) on the first 2000 characters of each line. A pattern over its time budget for a pass (one second in all over the lines matched) is turned off for the rest of the page's life, with a warning; one stuck in a single call is caught by a watchdog on the page, which stops the worker and starts a new one without that pattern (`lib/severity-highlighting.ts`). The decorations arrive a moment after the lines are drawn.

## Testing and CI

- **Tests never reach real remote hosts.** Connector and OIDC tests mock the SSH, SMB, WinRM, agent and IdP clients instead.
- **Grant resolution and rules are fully unit-tested.** Ordering, glob and regex mixes, the empty rule set, and folder-depth precedence must be correct before anything is built on them.
- **Pure logic in plain modules.** Frontend logic lives in pure, unit-tested `lib/*.ts` modules (for example `find-in-document.ts`, `tab-key.ts`, `connection-tree.ts`) rather than inside components.
- **Scoped e2e locators.** In e2e specs, look rows up by a specific element (for example the row's `.name`), not by the row's full text. A closed `<select>`'s options count as text and can match the wrong row.
- **Every archive endpoint needs permission.** The permission dependency was applied to every archive endpoint from the start.
- **Dependency scanning blocks the build in all three ecosystems.** `pip-audit` on `requirements.txt` and `requirements-dev.txt`, `npm audit --audit-level=high` (high and above, to avoid low/moderate transitive noise) and `govulncheck` (reachability-based, so more precise), as steps in the existing jobs that already have the toolchain. Since 0.7.0, `npm audit` runs through `.github/scripts/npm_audit.py`, so an advisory with no fixed version that doesn't reach what PerchTail ships can be accepted in `.github/npm-audit-exceptions.json`, with a reason and an expiry date, instead of blocking every build.
- **Container image scanned with Trivy.** CI builds the image locally (never pushed) and fails on HIGH/CRITICAL with `ignore-unfixed: true`. An unfixable OS-package advisory would otherwise block every build with nothing to do about it.
- **SBOM only as a CI artifact.** *Superseded:* with no release workflow, the CycloneDX SBOM was only uploaded per CI run; CI still does that, and `release.yml` now attaches SBOMs (image, backend, frontend, agent) to each release.
- **Dependabot weekly, targeting `dev`.** PRs go to `dev`, where development happens and every PR targets. *Superseded in scope:* it started with pip, npm and gomod only; it now also covers `github-actions` and `docker`.
- **MFA e2e uses its own browser context.** `e2e/mfa.spec.ts` signs its throwaway user in through `browser.newContext()`; logging out on the shared admin `page` would delete the stored session every later spec uses. Codes come from a small RFC 6238 generator (`e2e/totp.ts`, Node `crypto`) checked against `pyotp`, instead of a new dependency.
- **Viewer e2e writes fixtures into `LOG_DIR`.** `e2e/viewer-editor-features.spec.ts` drops timestamped JSON files into the system source's folder and removes them afterwards; the local connector reads straight from disk, so they show up like production files.
- **Real-browser E2E on top of unit tests.** A Playwright suite drives the real UI against a real backend across the whole admin surface, not only auth and the viewer. Backend unit tests prove a feature works, not that the page is wired to it (`frontend/e2e/`).
- **Isolated e2e backend.** `backend/scripts/run_e2e_server.sh` gives the e2e run its own `DATA_DIR`, SQLite database, credential salt, known hosts, log and scratch directories under `backend/data/e2e/`, wiped on every run. Each run starts clean and never touches a developer's data or instance lock.
- **Port 8001, not 8000.** The e2e backend listens on 8001 so it can run next to a developer's dev backend on the documented port 8000 (`frontend/playwright.config.ts`).
- **The e2e backend serves the built frontend; no Vite dev server.** The Vite proxy is hardcoded to `127.0.0.1:8000` and strips Origin/Referer to get past `OriginCheckMiddleware`. Serving `frontend/dist` from FastAPI gives one origin and no proxy, and exercises the same static-serving path production uses (`app/main.py` mount).
- **Known super admin seeded before startup.** `app/seed_e2e_admin.py` inserts a user with a known password before the lifespan runs, so `seed_initial_super_admin` does nothing and no random password has to be read from the logs. It refuses to run against a database that already has users, so it can never reset a real deployment.
- **Log in once, reuse the session.** A Playwright setup project (`e2e/auth.setup.ts`) logs in once and saves `storageState`, and every other spec starts already authenticated.
- **Real sshd and smbd from OS packages, not Docker.** `backend/scripts/setup_e2e_test_servers.sh` installs openssh-server and samba and runs them on non-privileged ports (2222, 1445), so the SSH and SMB connectors are tested against real protocol traffic. A CI runner needs only sudo, not a Docker daemon.
- **WinRM stays faked.** A real target needs a Windows host, which neither CI nor a Linux sandbox has. `app/testing/fake_winrm.py` replaces the connector's `_session` factory (the seam the unit tests patch) and is loaded only through `PERCHTAIL_TEST_PATCH_MODULE`, which only the e2e script sets and the docs say never to set on a deployment.
- **The throwaway OS account persists between runs.** The `e2euser` account and its Samba password survive between runs, while the sshd/smbd config, host keys and fixtures are recreated each time. Recreating a Linux user on every run is pointless churn, and only the script's own servers on its own ports authenticate against it.
- **Fixture files under `/tmp`.** sshd and smbd read the served fixtures as `e2euser`, who needs traverse permission on every parent directory, and a CI checkout usually doesn't allow that.
- **No Alembic step for the e2e database.** `init_db()` creates a fresh schema with `create_all` (plus the FTS5 index). Alembic is how an existing install upgrades, not how a new schema is created.
- **The browser install isn't baked in.** Neither `playwright.config.ts` nor the workflow hardcodes a preinstalled Chromium path. CI and contributors run `npx playwright install --with-deps chromium` (the `e2e` job does this).
- **Sequential specs (`workers: 1`).** Specs create, edit and delete shared admin state (sources, roles, users, alerts, system settings) on one backend, and determinism is worth more than the time parallel workers would save. Each spec uses uniquely named fixtures and cleans them up.
- **Separate `e2e` CI job.** It needs both the Python and Node toolchains, so it runs apart from the `backend` and `frontend` jobs (`.github/workflows/ci.yml`).
- **Hand-written TOTP in tests.** The MFA spec generates codes with `node:crypto` (`frontend/e2e/totp.ts`) rather than adding a dependency.
- **Audit-log specs make their own data.** `audit-log.spec.ts` writes a known entry through the retention control rather than relying on rows left by other specs, and checks that "Verify now" reports the chain intact.
- **Mutation testing deferred.** StrykerJS was considered with Playwright and not adopted; a mutation score means little until the test suite is broader. Nothing in the repo uses it today.
- **Still deliberately not covered end-to-end.** A real OIDC IdP round trip (`sso.spec.ts` covers settings, group mappings and a test connection that fails against an unreachable issuer) and a real push-agent connection (`agents.spec.ts` covers the upgrade settings with no agent connected). Each needs much heavier infrastructure; revisit if a regression gets through.
- **Second-user RBAC in the browser.** *Superseded (partly):* this used to be out of scope, on the grounds that `auth/rbac.py` unit tests cover grant resolution; `scoped-customers.spec.ts` now signs in as a delegated admin in a separate browser context and checks that only granted customers and folders are listed.
- **Content search e2e.** *Superseded:* `search.spec.ts` (indexing a source and deep-linking a hit) and the system-wide search toggle spec went with the content index; the file-name index and explorer search are covered by `explorer-search.spec.ts` instead (#303, #304).

## Operations (backups, upgrades, limits)

- **Packaging from day one.** Docker and docker-compose existed from the first milestone, so packaging wasn't a late surprise. PerchTail sits behind someone else's reverse proxy rather than shipping one.
- **App log rotation.** The app's logs use `structlog` JSON with a per-request `request_id`, gzipped rotation, and `LOG_RETENTION_DAYS` (default 30). Since then, size caps were added (`LOG_MAX_FILE_MB`, `LOG_MAX_TOTAL_MB`).
- **Load valves, not goals.** Size caps and truncation flags (scratch size guard, fetch limits) protect against pathological load. They are safety valves, not design targets.
